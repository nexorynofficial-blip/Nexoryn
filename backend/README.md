# Nexoryn Backend

Express + TypeScript + Prisma/PostgreSQL API for the Nexoryn website. Built
against the planning docs in [`../docs`](../docs) — read `docs/PRD.md` and
`docs/TRD.md` first if you haven't. This implements:

- Public read API for projects/case-studies, services, reviews, team.
- `POST /api/v1/contact` — persists every submission before attempting the
  admin-notification email, so a lead is never lost to an email-provider
  outage (see `docs/PRD.md` FR-8/FR-9).
- A full admin API (JWT-in-httpOnly-cookie auth) for managing all of the
  above, plus contact-submission triage, image uploads (Cloudinary), and a
  multi-admin finance/investment tracker with PDF/email reporting.

## Quick start

```bash
cd backend
bun install

cp .env.example .env
# fill in DATABASE_URL, JWT_SECRET, RESEND_API_KEY, CLOUDINARY_* — see the
# comments in .env.example for where to get each one.

# Local Postgres (skip if you already have one — just point DATABASE_URL at it)
docker compose up -d

bun run db:migrate      # creates the schema
bun run extract:frontend-data   # pulls real content from ../src/data/*.js
bun run db:seed         # loads it into the database + creates a seed admin user

bun run dev             # http://localhost:3001
```

The seed admin's email/password default to `nexorynofficial@gmail.com` /
`change-me-immediately` unless you set `SEED_ADMIN_EMAIL` /
`SEED_ADMIN_PASSWORD` in your shell before running `db:seed`. **Log in and
change it immediately if you use the default.**

## What `extract:frontend-data` actually does

Reads `../src/data/projects.js`, `services.js`, `reviews.js`, and the `TEAM`
array in `../src/pages/AboutPage.jsx` — the frontend's real, current content
— and writes it to `prisma/fixtures/*.json`, resolving the two things that
don't survive a plain Node `require()`:

- Every `lucide-react` icon import (e.g. `icon: Workflow`) becomes the
  plain string `"Workflow"`, matching how the backend stores icons (see
  `docs/DATA-MODEL.md` §2d and `src/utils/icons.ts`).
- Every image import becomes its relative source path as a string (e.g.
  `"src/assets/project-aurum-thumb.png"`) — **not** an uploaded asset.
  `db:seed` creates a placeholder `Asset` row pointing at that path for
  each one. Before going live, either upload the real files to Cloudinary
  and repoint those rows, or just re-upload each image through the admin
  panel once it exists — whichever is less friction for the team.

Re-run `extract:frontend-data` any time the live frontend's static data
changes and you want to re-sync (it's idempotent — `db:seed` upserts by
slug/displayId/name, it won't create duplicates).

## Project structure

```
backend/
├── prisma/
│   ├── schema.prisma       # full data model — see docs/DATA-MODEL.md for the "why"
│   ├── seed.ts             # loads prisma/fixtures/*.json into the database
│   └── fixtures/           # generated by extract-frontend-data.mjs, gitignored
├── scripts/
│   └── extract-frontend-data.mjs
├── src/
│   ├── app.ts              # Express app + all route mounting
│   ├── server.ts           # entry point
│   ├── config/             # env, Prisma client singleton
│   ├── middleware/         # auth, error handling, rate limiting, honeypot
│   ├── routes/
│   │   ├── public/         # projects, services, reviews, team, contact — no auth
│   │   └── admin/          # everything else — auth required
│   ├── services/           # email (Resend), storage (Cloudinary), validation (Zod),
│   │                        finance calculations, PDF report generation
│   └── utils/               # jwt, password hashing, typed API errors, icon-name validation
└── docker-compose.yml       # local Postgres for dev
```

## API reference

See [`../docs/API-SPEC.md`](../docs/API-SPEC.md) — every endpoint here
matches it exactly (a few admin routes — finance, internal-projects,
reports, FAQs — were added afterward per the team's separate backend
planning docs and aren't in that file yet; see the route files themselves,
they're small and self-documenting).

## Known gaps / next steps

- **Image upload during seed is a placeholder.** See "What extract does"
  above — real Cloudinary upload during seeding is a reasonable follow-up
  once credentials exist, using `src/services/storage.ts`'s
  `uploadToCloudinary` directly from `prisma/seed.ts`.
- **Naming inconsistency in the source data itself**: `Project.service` uses
  `"Brand & Graphic Design"` while `Review.service` /
  `ServiceCategory.serviceName` use bare `"Graphic Design"` — this is
  carried forward as-is from the live frontend (see
  `docs/DATA-MODEL.md`'s callout). Decide on one canonical string and
  migrate before this matters for anything (e.g. a future admin UI that
  cross-filters projects and reviews by the same service value).
- **No automated test suite yet** — `docs/TRD.md` §10 describes the
  intended strategy (validation unit tests, per-endpoint integration tests,
  a migration-parity test against the current static data) but no tests are
  checked in yet.
- **Finance/internal-projects/reports routes** implement the multi-admin
  profit-split/investment-tracking feature set from the team's separate
  planning docs — this is genuinely new scope beyond `docs/PRD.md`'s
  original public-site backend requirements, kept here because it was
  explicitly requested, but worth a look to confirm it's still wanted before
  building the admin UI for it.
